Chapter 08. 가드레일 · 8.2 데이터베이스 권한 격리 PostgreSQL / Supabase RLS

RLS(Row Level Security) 누수 방지: 3대 치명적 함정과 방어 DDL

BaaS 환경에서는 프론트엔드가 DB에 직접 쿼리를 날립니다. 백엔드 방화벽이 없으므로 DB 자체에 방패를 씌워야 합니다.

PITFALL 01. 비활성화 기본값 기본 공개 위험

ENABLE RLS 누락의 참사

PostgreSQL은 테이블 생성 시 RLS가 기본적으로 OFF 상태입니다. AI에게 그냥 테이블을 만들라고 하면 누락되어 anon 키로 전 고객 데이터 조회가 열립니다.

-- ❌ AI가 흔히 짜는 취약한 SQL
CREATE TABLE profiles ( id uuid, ... );
-- ✅ 필수 1줄: RLS 강제 활성화
ALTER TABLE profiles ENABLE ROW LEVEL SECURITY;
  • • 결과: RLS 활성화 없이는 아무리 복잡한 정책을 써도 0% 적용.
  • • 규칙: 모든 DDL 마이그레이션 끝에 ENABLE RLS 필수 강제.
⚠️ RLS 누락 시 브라우저 콘솔에서 전체 DB 덤프 가능
PITFALL 02. 반쪽짜리 정책 CRUD 누락

SELECT만 막고 UPDATE 방치

AI는 종종 FOR SELECT 정책만 달랑 작성합니다. 이 경우 인증된 사용자가 타인의 결제 금액이나 상태를 UPDATE 해버리는 권한 상승 버그가 발생합니다.

-- ❌ 타인 프로필 변조 가능 구멍
CREATE POLICY p1 ON users FOR SELECT...
-- ✅ CRUD 전체 격리 (INSERT, UPDATE, DELETE)
CREATE POLICY p_all ON orders FOR ALL
USING (auth.uid() = user_id)
WITH CHECK (auth.uid() = user_id);
  • • USING vs CHECK: 읽기/삭제 조건(USING)과 쓰기/수정 조건(WITH CHECK) 동시 검증.
⚠️ FOR ALL 정책으로 4대 작업(CRUD) 완전 격리 필수
PITFALL 03. 키 오남용 Superuser 유출

Service Role Key 프론트 번들링

AI가 RLS 권한 에러를 만나면, 원인을 해결하는 대신 모든 RLS를 우회(Bypass)하는 마스터 키인 service_role 키를 클라이언트에 주입해버립니다.

Client 번들 anon key만 허용 (RLS 작동)
Server / Admin service_role (절대 노출 금지)
🚨 service_role 노출 시 RLS가 100% 무력화되어 관리자 권한 탈취!
  • • 규칙: 프론트엔드는 반드시 anon key + 유저 JWT 세션으로만 접속.
⚠️ service_role 키는 오직 백엔드 서버 환경변수에만 존재해야 함
🛡️ DB 가드레일 골든 룰: "테이블 생성 시 ENABLE RLS와 auth.uid() = user_id 정책이 없으면 CI 파이프라인에서 커밋 거부."
