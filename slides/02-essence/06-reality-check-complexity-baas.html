2.4 이상과 현실 (Reality Check) : ① 자연어의 한계 vs ② BaaS 레고 블록 전략

단일 파일 토이 데모를 넘어, 실제 유저와 트랜잭션이 붙는 순간 발생하는 소프트웨어 복잡계의 벽:

쟁점 ① COMPLEXITY WALL 자연어의 한계

'말만 하면 된다'는 환상 vs 복잡계의 벽

환상: "이제 코딩을 전혀 몰라도 아이디어와 자연어 프롬프트만 있으면 바로 서비스가 완성된다."
🚨 1. 단일 토이 vs 프로덕션 복잡계

1개 파일짜리 데모는 쉽지만, 실제 서비스는 상태 관리(State), 네트워크 예외 처리, 비동기 파이프라인, 빌드 환경이라는 거대한 복잡계를 반드시 통과해야 합니다.

🚨 2. 컨텍스트 표류 (Context Drift)

프롬프트에만 의존할수록 세션이 길어지면서 AI가 이전 설계를 잊어버리고, 앞선 코드를 덮어써 버리거나 엉뚱한 라이브러리를 재설치하는 기억 상실이 발생합니다.

"자연어는 모호성을 허용하지만, 컴파일러와 런타임은 단 1비트의 모호성도 허용하지 않는다."
쟁점 ② ARCHITECTURE STRATEGY 현실적 해법

바닥부터 구축 vs 현대 BaaS 레고 블록 조립

환상: "AI 에이전트에게 DB 스키마, 인증 서버, 결제 연동, 메일 발송 서버를 전부 작성하라고 시킨다."
⚠️ 바닥부터 백엔드를 짜면 설계 파탄

인증 세션 토큰 관리, DB 커넥션 풀링, 트랜잭션 격리 수준을 AI에게 바닥부터 맡기면 취약점과 병목이 폭발합니다.

✅ 바이브 코더의 생존법 : 글루 코드(Glue Code)

이미 수만 개 기업에서 검증된 클라우드 서비스(Vercel + Supabase + Clerk + Stripe)를 프롬프트로 엮어내는 것이 유일하게 안전한 전략입니다.

📌 Takeaway: 프롬프트는 '모든 것을 만드는 요술봉'이 아니라, '검증된 컴포넌트를 조립하는 접착제(Glue)'로 사용해야 성공합니다.
